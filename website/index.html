Fraction Bazaar

A single-page web app that teaches a 9-year-old fraction equivalence end-to-end: a splash, a from-zero scripted lesson, a six-slide tutorial, a polyomino placement game with strict color rules, and a bazaar-vendor trading game with an LLM-scored remediation lesson. One Render service. Four routes. Three different state libraries by design.

Layered model

Domain

Pure value objects

Fraction, Polyomino, Grid, Piece, Rule in Boxy; Fraction, Vendor, Customer, TrayPiece in Trade. Every invariant lives here. The domain throws clear exceptions on misuse so a UI bug surfaces with a stack trace that names the offending call site.

State

Observable container

Boxy uses Zustand (cheap, no provider, selector-based). Trade uses XState v5 (8 screen states with event guards). Lesson uses a 30-line useReducer. The libraries do not cross-pollinate — each game owns its store behind its own route.

UI

Dumb renderers

React components subscribe to slices of state. They render and dispatch, nothing else. No data fetching for any client-only flow. The only server endpoint is /api/validate, called once per missed Trade Mogging serve.

Three games, three state libraries

Each game's state shape made a different library the right tool. The pluralism is intentional. Each lives behind its own route; the libraries do not interact.

Lesson
useReducer

11 phases, each with a small bag of UI state (split count, fill count, chat-done flag, remediation string). 5 action types cover it.

Pros
  • 30 lines, zero dependencies
  • Co-located with the component
  • TypeScript checks each action shape
Cons
  • Reducer grows with each new advance kind
  • Manual rerender management for chat cadence
Boxy
Zustand

Round, grid, tray, messages, terminal-state flags, miss counter, max-possible-fill ceiling. Many components subscribe to small slices.

Pros
  • No Provider boilerplate
  • Cheap selector subscriptions
  • setState fits the immutable-update flow
Cons
  • Selector allocation is a footgun (React error #185)
  • No native event-graph support
Trade
XState v5

8 discrete screen states connected by event guards (isMog, isProfit, hasMoreCustomers).

Pros
  • State chart visualizable
  • Guards prevent illegal transitions at the source
  • Pure context, no side-effects until needed
Cons
  • Heavier learning curve than useReducer
  • v5 API differs from older XState docs

Boxy placement contract

Snap-to-legal drop + strict per-edge color match. The flow tries every local cell of the piece as the hot-spot, scores each by piece-centroid-to-drop-cell distance, and picks the best legal candidate. Rejections rank from rule-mismatch through bounds-check.

Snap-to-legal

The drop cell is the cell under the pointer, not the piece's (0,0). Trying every local cell as the hot-spot eliminates the false "out of bounds" / "spot taken" errors that fired when the visual drop was on a valid cell but the top-left corner landed off-grid.

Strict edge contract

Each cell-edge between new piece and neighbor: both blank → ok; one blank, one colored → reject; different colors → reject; same color → that color's specific rule must hold for the count ratio (equivalents like 6:10 ≡ 3:5 count).

Miss counter

Every rejection bumps missCount. The toolbar's stat chip stays gray at 0 and tints honey above zero. Soft pressure against drag-and-pray, not punishment. Resets on Reset and New round.

Trade Mogging state machine

8 discrete screen states. The machine is the only thing that mutates Trade Mogging state. UI components are pure renders of the snapshot.

Data flow on a missed Trade Mogging serve

The kid never sees the LLM's prose. The frontend maps the integer 1-5 score to one of five pre-written scripted responses. The LLM's pedagogical judgment is used; its writing is not.

Trade-offs we accepted

Three state libraries inside one app

Zustand for Boxy, XState for Trade, useReducer for Lesson. Pluralism is intentional — each library fits its game's state shape — but onboarding takes longer.

Why I accept it

Each game lives behind its own route; the libraries do not cross-pollinate.

When it would bite

A new contributor has to learn three idioms before they can move across the codebase.

Boxy tests live in a separate repo

The standalone boxy-fractions repo has a Vitest suite. Porting Vitest into this repo is a follow-up.

Why I accept it

The domain layer is identical and the source-of-truth tests still gate that repo.

When it would bite

A regression in this repo's port would not be caught by its own CI until the test suite ports too.

No persistence

A kid who closes the tab and comes back starts fresh.

Why I accept it

Off-ramp principle (Skinner): a paused lesson is a finished lesson.

When it would bite

A parent who wants "save progress" needs a v1.1 with its own auth and design implications.

Anthropic API key gates Trade rubric

If the key is unset, the lesson degrades to keyword fallback.

Why I accept it

Three-tier defense (strict JSON → regex → loose digit) plus keyword fallback means the game never breaks; the rubric just gets coarser.

When it would bite

A missing key on production is invisible until a kid hits the lesson panel; /healthz reports it.

Character art is placeholder-grade

Hand-drawn SVG carries the bazaar's design rules but was called out by the user as needing polish.

Why I accept it

No external assets, deterministic, no licensing — the gameplay flow ships first.

When it would bite

Cowork MCP registry has no text-to-image generator; richer art needs a Replicate / Fal.ai / DALL-E MCP installed at the Claude Desktop level.

Lesson bar is tap-only

A drag-drop bar would feel more tactile but doubles the implementation surface.

Why I accept it

Tap-to-split + tap-to-deposit covers the pedagogy with one event type and one accessibility story.

When it would bite

Re-evaluate on iPad after first cohort tests if kids ask for "drag the pieces in."

Cost model

Only Trade Mogging incurs per-request cost (one Claude Haiku call per missed serve). The lesson, tutorial, and Boxy run entirely client-side. Render Starter plan covers always-on at flat $7/mo.

Per-request cost by route

Claude Haiku 4.5 priced at $1/M input + $5/M output tokens (May 2026 list). System prompt + user message ≈ 250 input tokens; reply ≈ 12 output tokens. ≈ $0.0003 per missed serve.

Monthly cost at scale

Assumes ~3 missed serves per kid per session, one session per kid per day. Log-axis. Render + Anthropic combined.
